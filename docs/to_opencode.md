# E1 — evolve kernel_opmap.py into the native-operation code generator

**Task for OpenCode.** Work in `pereuna/Plan2001-O`, current main. D2b is finished; **D2c is deferred**. Start the first reversible experiment towards a pathless kernel driver interface. This task is about building/reusing a mechanical *source transformation tool*, **not** booting another console demo or porting 27 drivers manually.

## Nonnegotiable design choice: ONE analyser

The repository already contains:
- `tools/kernel_opmap.py` (~4,000 lines): real Plan 9 C tokenizer/parser, build membership, `Dev` registrations, `Dirtab`, `Cmdtab`, Qid branches, indirect callbacks, call graph; current JSON/Markdown renderers and deterministic source fingerprint;
- `tools/test_kernel_opmap.py` (focused fixtures/tests);
- `docs/KERNEL-OPMAP.{json,md}` and `docs/KERNEL-OPMAP-NOTES.md`;
- `docs/CHAN-DEPENDENCIES-INDEX.md` recording an **external** lexical Chan-dependency audit at older commit `19de707`. Its 41k-line raw artifact is NOT in the repo and was NOT generated by `kernel_opmap.py`.

**Evolve this existing analyser into the generator's frontend. Do not implement a second competing kernel scanner, second copy of the call graph, or an obsolete `tools/*` inventory script.** Keep `tools/kernel_opmap.py` as the entrypoint and reusable analysis implementation. You may extract cohesive modules into a small `tools/kernel_opmap/` package **only if demonstrably needed**, keeping CLI compatibility and no third-party runtime dependency. Resist a general framework or major reorganizing patch.

Understand the present scanner's limitations before generating C: lexical/structural only, NOT preprocessed typed AST, no proof of semantic equivalence; the source-specific GEFS `Chan/Mount/Path` macro aliases are NOT kernel `Chan`; indirect callbacks, alternative `#if` branches and actual link membership require explicit uncertainty. Never infer safe code from coincidentally matching function names.

## Architectural semantics

We remove **compulsory directory/namespace traversal**, not files or streams:
- `Qid.path` may encode a useful **numeric device operation selector**; do not equate Qid with an OID or insist on deleting numeric selectors.
- persistent OIDs name stored content; ephemeral device instances/streams have process-local resource identities and rights, potentially without OID;
- `Chan` is a conglomerate of device instance state, identity, access mode, offsets, mount/path, refcount, locks etc. It must NOT be blindly text-replaced.
- distinguish **DIRECT** (actually pathless AND Chan-independent), **BRIDGE** (pathless entry still internally uses Chan), **MANUAL** (unsafe/unproven automatic migration), **LEGACY** (only namespace implementation and not required by native O boot).
- A C function that compiles is not proof of equivalent operation, permissions, resource lifetime or IRQ/DMA/locking behavior.

## Implementation scope, E1 (not a wholesale driver conversion)

1. Read `AGENTS.md`, brief `docs/STATUS.md`, `docs/KERNEL-OPMAP-NOTES.md`, `docs/CHAN-DEPENDENCIES-INDEX.md`, `tools/kernel_opmap.py`, `tools/test_kernel_opmap.py`; check `git status --short` and real HEAD. Never reset or stage unrelated work.

2. Reuse `Analyzer(...).analyze()` (or refactor that interface without duplicating parsing) to construct an **intermediate operation specification** for active `pc64` drivers. Include: source/function/line, device identity, selected Qid or command, read/write/control semantics, conditional build status, backend call/callback evidence, path/Chan dependencies, permission/lifecycle and state risks, conversion status **and reasons**. Preserve source hash and provenance. Refuse unknown/ambiguous cases explicitly. Do not mark a driver DIRECT just because one `switch` was recognized.

3. Add an **opt-in generator mode** to `tools/kernel_opmap.py`, e.g. `--generate-native --out-dir build/generated/kernel-native` (you may choose a clearer equivalent); default `--write`, `--check`, `--stats` and current deterministic OMAP JSON/MD MUST still behave as before. The generator must use the same parse/IR and produce reproducible, inspectable generated C header/source plus a compact machine-readable decision manifest. No generated files in source driver directories. Generated build output must be kept under `build/` (ignored by Git), not included in kernel build by default. Use Python standard library only.

4. **Small real pilot: `sys/src/9/pc/devrtc.c`.** The current device has static `rtcdir`, Qrtc/Qnvram branches, and hardware helpers. Analyze its `walk/stat/open/read/write` interface and identify precisely the portions implementing (a) name traversal and (b) hardware action, permissions, resource bounds, offsets, and locking. Generate at least a compilable native C **entry/interface** for the known selector mapping and operation signatures without introducing `walk/namec`/directory lookup. For actual operation bodies, only generate DIRECT calls when the target is proven accessible and equivalent; otherwise provide a **small explicit verified native helper extraction / reviewed binding**, or mark the operation MANUAL, with a reason. No `return 0` success stubs, no fake hardware operation, no silent loss of `eve` permission checks. An automatically generated typed declaration alone is not a claim that the function works. Ideally demonstrate one genuinely callable read operation through the new interface under a controlled test/compile; if impossible without risky changes, record E1 PARTIAL and a minimal necessary human-reviewed extraction step. Avoid a new syscall and don't grant users blanket access to RTC/NVRAM.

5. Run the identical analysis on **`devpipe.c`**, but only classify its dynamic endpoint ownership/open-close semantics; do not blindly autogenerate its FIFO runtime. Report what blocks safe automation. Report status coverage for the other active drivers but do not edit them.

6. Expand `tools/test_kernel_opmap.py` with fixtures covering deterministic C generation, Qid/Dirtab mapping, ambiguous callback or macro alias refusal, conditional branches, permission/offset semantics in the manifest, and generation/checking from repeated runs. Validate generated C with the repository's actual Plan 9 C toolchain when practical, not a guessed GCC dialect. Do not use `regex` substitutions as a code converter without token/semantic guardrails. Fail closed on unresolved source edits.

7. Run `python3 tools/test_kernel_opmap.py`, `python3 tools/kernel_opmap.py --check`, generated-output comparison twice, and `WHAT=kernel tools/build.sh` if any C/kernel file changes. Re-run D2b server gate only if changing executable/kernel behavior; if not run, say so. Do not silently regenerate huge OMAP artifacts unless their source fingerprint/schema genuinely changed; preserve `--check` meaning.
